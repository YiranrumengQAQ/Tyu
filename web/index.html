JLC 隔离游乐场

每个演示应用都是一个真实页面：内联 .jbc 字节码 + 只含运行时的 jlc-runtime.js， 被本页用 sandbox="allow-scripts" 的 iframe 装进来。于是同一次「拒绝」可能来自三层： 浏览器沙箱（opaque origin，拿不到宿主 DOM / storage）、内核策略（profile + fault 档）、 编译期硬限制（innerHTML、javascript:、<script>，任何档都拒绝）。 开关改的是后两层，自检面板看的是第一层。

全局开关

strict = 0.2 的行为；open 打开 frame / data: / 窗口事件 / 富文本；trusted 只在受信构建里用。

stop：装载前整体抛错，一个节点都不渲染。degrade：被拒接口换成 <jlc-denied> 占位、副作用跳过并记账。report：照常渲染，只记录。

strict 时挂载点之外的 DOM 一律 JLCIsolationError，被移出隔离域的节点自动 dispose。

实例累计指令数上限：给失控的 every / 递归 action 兜底。

覆盖优先于档位；解析失败就退回档位名。例：{"allowDataUrls": false}。

勾上后沙箱框架不再是 opaque origin：下面的自检会立刻出现「leaked」行——这正是要看的东西。

事件日志

这页怎么来的

web/apps/*.jlc 是源；npm run build:web 用仓库里的真编译器生成 web/apps/*.html（内联 base64 .jbc）、web/jlc-runtime.js（仅 VM）、 web/jlc-full.js（编译器 + VM）与 web/registry.js。npm run check 会跑 --check 防漂移。 产物零网络请求，所以 file:// 直开也能玩；起本地静态服务器则会带上 COOP/COEP，右上角的 crossOriginIsolated 变绿。

编译台 · 宿主有编译器，沙箱页没有

编译发生在控制台（同源、有编译器），产物 .jbc 通过 postMessage 注入沙箱页；沙箱页只带运行时，无法自行编译——这正是部署形态。
