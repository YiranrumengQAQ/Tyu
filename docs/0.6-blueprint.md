# JLC VM 0.4 → 0.6 内核改造蓝图

> 目标读者：维护 `jlc-vm.js` 的人。
> 本文对着**真实实现**写：每个符号都能在仓库里搜到，每个「已完成 / 未完成」都有代码或测试作证。
> 硬约束：**纯前端 / GitHub Pages / 零后端 / 不碰 VPS**，`.jbc` 仍是静态文件。

```
                    GitHub Pages（静态分发层）
                             │
                    ┌────────▼────────┐
                    │   JLC OS Shell  │   ← web/0.5 的 Capability Hub 继续可用
                    └────────┬────────┘
                             │  mount(module, target, options)
                    ┌────────▼─────────────────────────────────┐
                    │            JLC VM 0.6（jlc-vm.js）        │
                    │                                          │
                    │  Verifier(11 趟) → Linker → Machine      │
                    │      │                │                  │
                    │      │          Scheduler v2（P0..P7）    │
                    │      │                │                  │
                    │  Security        Resource       Host     │
                    │  ├ Policy        ├ 账本/限额     ├ DOM    │
                    │  ├ Capability 图 ├ ENOSPC_QUOTA ├ Storage │
                    │  ├ Permission K. ├ 检查点       ├ Network │
                    │  └ Isolation     └ 故障阶梯     └ Browser │
                    └────────┬─────────────────────────────────┘
                             │  只有内核授权的宿主能力才能穿过
                    JLC Apps（.jlc → .jbc，全部静态文件）
```

## 0. 版本与 ABI 现状

| 常量 | 0.4 | 0.6（现在） |
| --- | --- | --- |
| `VERSION` | `0.4.0` | `0.6.0` |
| `BYTECODE_VERSION` | `2` | `3` |
| `ACCEPTED_BYTECODE_VERSIONS` | `[1, 2]` | `[1, 2, 3]` |
| `ABI_VERSION` | `jlc-abi/2` | `jlc-abi/3` |

**兼容规则（已实现并有测试）**

* v1 / v2 模块继续装载：缺的段由验证器从指令流重算补齐（`module.capabilityPaths`）。
* v3 新增三个段，旧的 `SECTION` 编号一个都没动，所以 v3 解码器读 v2 文件是纯缺省路径。
* 版本号高于内核（例如 9）→ `JLCVerifyError`，不误解码。
* **解码器跳过未知段**：这是分发场景下唯一正确的选择，否则任何一次内核增量都会让旧文件失效。

### ABI v3 的三个新段

```js
const SECTION = { POOL: 1, GLOBALS: 2, FUNCS: 3, ACTIONS: 4, DECLS: 5, VIEW: 6, META: 7, MANIFEST: 8,
                  CAPABILITIES: 9,  // 能力图路径清单（str 数组）
                  RESOURCES: 10,    // 资源清单：kind:u8 + 静态上界 u32
                  FLAGS: 11 };      // u32 位图
```

| 段 | 内容 | 谁生成 | 谁核对 |
| --- | --- | --- | --- |
| `CAPABILITIES` | `["network.http", "compute.timers", …]` | `analyzeModule()`（指令流扫描） | `verifyModule()`：申报**只能少报不能多报**，漏报即载入失败 |
| `RESOURCES` | `dom/effects/timers/requests/styles` 的静态上界，由 `resourceManifestOf()` 数指令算出 | 同上 | 申报了却完全用不到的 kind 视为伪造 |
| `FLAGS` | `deterministic / network / timers / frames / windowEvents / workers` | 同上 | `analyzeDeterminism()` 给出人话原因 |

## 1. 逐模块改造表（保留 / 重构 / 新增）

| 模块 | 0.4 的东西 | 0.6 处置 | 落点 |
| --- | --- | --- | --- |
| 二进制容器 | `ByteWriter/ByteReader/encodeModule/decodeModule` | **保留**，追加 3 个段 + 未知段跳过 | `SECTION.*`、`resourceManifestOf()` |
| 验证器 | `verifyModule`（线性扫描 + 栈深度工作表 + 结构引用） | **重构为 11 趟**，原逻辑一行没删，新增 5 趟分析 | `VERIFIER_PASSES`、`buildCFG()`、`analyzeAbstractStack()`、`analyzeModule()`、`verifyReport()` |
| 反汇编器 | `disassembleModule` | **保留**，追加 `.capabilities` / `.resources` | 同文件 |
| 策略 | `resolvePolicy / policyViolation / checkPermissions / guardSurface` | **保留**，新增 `capabilities` / `resources` / `permissionStrict` 三个字段；`guardSurface` 接入权限内核 | `POLICY_KEYS`、`normalizeCapabilityGrants()`、`normalizeResourceLimits()` |
| 能力授权 | `capabilityAllowlist`（一张白名单） | **升级为** `CAPABILITY_TREE` 树 + `PermissionKernel` 状态机 | `CAPABILITY_PATHS`、`PERMISSION_STATES` |
| 配额 | `maxDomNodes / maxStyleBytes / maxTotalSteps` | **收拢为** `ResourceKernel` 账本 | `RESOURCE_KINDS`、`DEFAULT_RESOURCE_LIMITS` |
| 调度器 | `Scheduler`（单队列 + 优先级数字 + 1000 轮保护） | **重写为 v2**：8 通道 + 任务层 + 预算/截止时间 + 让出接管；`queue/pending/enqueue()` 旧语义原样保留 | `PRIORITY`、`TASK_PRIORITY`、`normalizePriority()` |
| 执行机 | `Machine.dispatch`（`stack / frames / ip`） | **加法**：`dispatchDepth`、`sliceableTask`、`suspended` 现场、`resumeSuspended()`；关闭切片时路径与 0.4 完全一致 | `Machine.suspend/resumeSuspended/beginSlice` |
| 故障 | `fault: stop / degrade / report` | **升级为 6 级阶梯**，旧档名自动映射 | `FAULT_LEVELS`、`FAULT_ALIASES`、`normalizeFaultLevel()`、`Runtime.handleFault()` |
| 容错 | 无 | **新增** Error Boundary（组件级 `restart`）与快照回滚 | `Runtime.restartScope()`、`CheckpointStore` |
| 诊断 | `handle.inspect() / describe()` | **新增** 只读视图，默认零开销 | `Runtime.profile() / snapshot()`、`VMKernel.graph() / verify() / profileAll() / resources()` |
| DOM / 视图 | `DOM_OPS`、`EACH`、`WHEN` | **保留**，追加 `replay` 钩子（组件重启的落点） | `OP.WHEN` / `OP.EACH` 处理器 |
| 编译器 | `jlc-compiler.js` | **未改动**（v3 段由 VM 侧生成，编译器无需知道） | — |

## 2. 验证器：11 趟（`VERIFIER_PASSES`）

| # | 名称 | 做什么 | 失败语义 |
| --- | --- | --- | --- |
| 1 | `header` | `format === "jlc-bytecode"`、常量池存在、池/函数/全局表上限 | 硬失败 |
| 2 | `pool` | 常量池条目类型；字符串可被 `requirePooled` 引用 | 硬失败 |
| 3 | `opcode` | 操作码合法性 + 「这个 opcode 允许出现在 expr / body / view 吗」 | 硬失败 |
| 4 | `operand` | 操作数越界、`P/F/R/S` 索引范围、槽位边界 | 硬失败 |
| 5 | `stack` | 工作表算法的栈深度一致性 + 视图元素游标配平（0.4 原有实现） | 硬失败 |
| 6 | `cfg` | 基本块、边、不可达块、循环回边、跳转落在指令边界 | 默认 advisory，`mode: "strict"` 升级 |
| 7 | `types` | 抽象栈类型：只在**确定类型冲突**时报（把数字当函数调、对确定 null 取成员） | advisory / strict |
| 8 | `structure` | action→body、declaration→expr、view→view 的引用完整性 | 硬失败 |
| 9 | `manifest` | 接口清单 + 能力清单与指令流交叉核对（申报不能多报） | 硬失败 |
| 10 | `security` | 常量池里的原型逃逸键与脚本型 URL 前缀 | warning |
| 11 | `determinism` | 有没有 timer / http / frame / 窗口事件 → 能不能被快照重放 | 只读结论 |

```js
const report = JLC.verify(program);        // 永不抛异常
report.ok;                                 // true
report.passes;                             // 11 趟各自 ok / label
report.analysis.functions;                 // 每个函数的 blocks / edges / loops / unreachable
report.analysis.capabilityPaths;           // 能力图路径
report.analysis.determinism;               // { deterministic, reasons }
JLC.graph(program);                        // CFG 文本 dump（人类可读）
```

### CFG 算法（Pass 6，`buildCFG`）

1. **Pass A 线性解码**：记录每条指令的 `start/end/values/jump`。
2. **块首** = 函数入口 ∪ 跳转目标 ∪ **终结指令的下一条**。
   （踩过的坑：一开始把「每条指令的末尾」都当块首，结果每个 opcode 一个块、还生成了大量假不可达块。）
3. **Pass B 切块**：从块首走到终结指令；切块判据用 `leaders.has(cursor)`，**不能用**「已建块表」，因为块是按起始地址顺序建的，后面的块首还没进表。
4. **Pass C 连边**：`always → target`；`branch → [target, fallthrough]`；`fornext → [exit, fallthrough]`；`return → exit`；其余落到紧随其后的块（要求 `next.start === block.end`）。
5. **Pass D 可达性 + 回边**：BFS 求可达；`target.start <= block.start` 的边记作循环回边。

### 抽象栈类型（Pass 7，`analyzeAbstractStack`）

类型格：`null / bool / number / string / array / object / function / unknown`。
所有拿不准的一律落到 `unknown`，**只有确定冲突才报警**——这是把静态检查塞进既有编译器的唯一安全姿势。
`mode: "strict"` 时升级为载入失败，可放进 CI。

## 3. 能力图与权限内核

### 3.1 能力树（`CAPABILITY_TREE` / `CAPABILITY_PATHS`）

```
dom            read · create · update · remove
network        http · websocket · stream
storage        memory · session · indexeddb · cache · transaction · migration
filesystem     read{picker,stream} · write{picker,stream} · directory{read,write} · download
browser        navigation · title · clipboard{read,write} · fullscreen · notification
               share · theme · pwa · serviceWorker · window
device         camera · microphone · geolocation · sensors · vibrate · platform
compute        worker · ipc · timers · frame · crypto · compression
process        appManager · permissionManager · inspector · debugger
```

* 路径是**内核唯一权威**：`isCapabilityPath()` 之外的东西，宿主也发明不出来。
* 祖先授权：`filesystem.read` 授予即覆盖 `filesystem.read.picker`（`PermissionKernel.check` 逐级上溯）。
* 旧宿主零改动接入：`CAPABILITY_ALIASES` 把 0.5 Capability Hub 的裸名字（`storagePut`、`clipboardWrite`、`fileOpen`…）映射到路径；也可用 `capabilityPaths` 选项覆盖。

### 3.2 权限内核（`PermissionKernel`）

```
requested → granted / session / once / persistent
              │            │
              │            ├─ 租约到期 → expired（惰性判定，不需要定时器）
              ├─ denied ───┤
              ├─ suspended │
              └─ revoked ──┘   ← 运行中撤销，后续每一次调用立刻失败
```

```js
const app = program.mount(target, {
  capabilities: { storagePut, clipboardWrite },        // 裸名字（旧宿主原样可用）
  capabilityPaths: { storagePut: "storage.indexeddb" }, // 名字 → 路径
  grants: { "storage.indexeddb": { mode: "session", expires: Date.now() + 3_600_000 } },
});

app.revoke("storage.indexeddb");   // 立刻生效：不再调用宿主的 storagePut
app.grant("browser.notification"); // 也可以事后补授权
app.capabilities();                // [{ path, state, granted, mode, expires, calls, denials }]
```

**关键裁决：权限内核的决定不受 `fault` 档影响。** 策略拒绝走故障阶梯（`recover` 可以「记录后放行」，兼容 0.4 的 `report`），但**撤销 / 暂停 / 租约到期必须立刻拦停**——否则「运行中撤销授权」只是一句空话。

## 4. 资源内核（`ResourceKernel`）

```js
RESOURCE_KINDS = ["cpu","memory","dom","effects","scopes","styles","timers",
                  "listeners","requests","streams","workers","storage","tasks","checkpoints"]
```

* 用量来源分两类：**派生**（直接读 `runtime.metrics`：dom / effects / scopes / styles / timers / listeners / requests / tasks）与**显式计数**（cpu / streams / workers / storage / memory）。
* 唯一出口是 `reserve(kind, amount)`：越界抛 `JLCQuotaError`，`code = "ENOSPC_QUOTA"`，并附带 `resource / limit / used`。
* 记账点：`Scope` 构造、`Effect` 构造、`createTimer`、`listen`、resource 请求、`registerOwnedNode`（DOM 节点配额前移到创建之前，失败时不再留下半条账）。
* 视图：`handle.resources()`、`describe().resources`、`JLC.resources()`（全内核汇总）。

```js
program.mount(target, { resources: { effects: 8, requests: 4, dom: 50_000 } });
// 或走策略：resolvePolicy({ profile: "open", resources: { effects: 8 } })
```

## 5. 调度器 v2 与协作式让出

### 5.1 8 条通道

```
P0 SYSTEM  内核自身（初始化、链接）
P1 INPUT   用户输入（点击、键盘、指针）
P2 INTERACTION  宿主调用（handle.call）
P3 RENDER  视图渲染、派生状态
P4 EFFECT  响应式副作用
P5 NETWORK 请求回调
P6 BACKGROUND  定时器、后台计算
P7 IDLE    可以等到没人的时候
```

数字越小越先跑，与 0.4 的 `priority` 数字**同序**，旧代码零改动。
`normalizePriority()` 同时接受数字、别名（`"render"`）与 `PRIORITY.*`。

### 5.2 任务层（`Scheduler.submit` / `Runtime.perform`）

```js
runtime.perform({
  kind: "interaction",        // → 默认通道
  priority: PRIORITY.INPUT,   // 可覆盖
  budget: 200_000,            // 指令预算（0 = 不限）
  deadline: performance.now() + 8,
  sliceable: true,            // 允不允许协作式让出
  run: () => machine.runView(...),
  then: (value) => { /* 内核 JS 收尾步骤 */ },
});
```

`then` 是关键设计：VM 挂起时 JS 栈会被 unwind，收尾步骤必须能被异步重放，
所以内核把「跑完之后要干的那几件事」显式交给任务层。

### 5.3 协作式让出（Cooperative Yield）

```
dispatch 内层循环
  每 SLICE_CHECK_INTERVAL(512) 条指令 ↓
    预算 / 截止时间还够？ ── 够 ──→ 继续
            │
            不够
            ▼
    frame.ip = ip              （保存指令指针）
    Machine.suspend()          （保存 frames / stack / context / render / actionDepth / entryFrame）
            │  JLCYieldSignal（控制流，不是错误）
            ▼
    调度器 adoptSuspension() → 续跑任务（通道 +1，让别的通道先跑）
            │  微任务
            ▼
    Machine.resumeSuspended() → 从 ip 继续，直到返回
```

**可续跑规则（安全底线）**：只有「最外层 dispatch + 显式可切片任务」才允许让出。
嵌套 dispatch（effects 内部的 `runView`、`each` 的 JS 循环）不允许让出——
那些 JS 局部状态无法重放。这类路径超预算时抛 `JLCBudgetError`（`E_BUDGET`），
交给故障阶梯（recover / restart / rollback / stop），**绝不静默丢状态**。

**零开销**：不设置 `maxSliceSteps` / `frameBudgetMs` 时，`sliceEnabled` 为常量假，
内层循环只多一个可预测分支；已用 200 次重负载 action 对比 0.4 内核，无可测差异。

```js
const app = JLC.mount(src, target, { maxSliceSteps: 50_000, frameBudgetMs: 8 });
const promise = app.call("crunch");   // 会切片时返回 Promise；否则照旧返回同步值
await promise;
app.profile().counters.yields;        // > 0
```

## 6. 故障阶梯与容错

```
ignore    不拦不记（仅调试）
degrade   跳过这一步，实例继续（可授予能力被收回）
recover   放行 + 记账 + 上报宿主 —— 0.3/0.4 的 report 就落在这一级
restart   只销毁出错组件，原地重建（Error Boundary）
rollback  回到最近的运行时检查点
stop      卸载实例（内核不变量已不可信）
```

* 旧档名映射：`report → recover`、`throw/fail/abort → stop`、`skip → degrade`。
* 内核不变量违规（`JLCVerifyError` / `JLCIsolationError`）**永远 stop**，与 `fault` 档无关。
* 组件级重启的落点：`OP.WHEN` 的分支与 `OP.EACH` 的列表在创建作用域时登记 `scope.replay`。
  `Runtime.restartScope()` 找到最近的重放拥有者 → 销毁出错组件 → 重放；
  单个作用域连续重启超过 3 次就退到下一级，避免「重启 → 再炸 → 再重启」死循环。
* **踩过的坑**：重启请求是在出错组件内部发出的，外层 JS 还会继续往下跑（把 `current` 写回旧值）。
  所以 WHEN 的重建用**强制重建令牌** `forceRebuild` 而不是「比较状态」。

### 检查点 / 回滚（`CheckpointStore`）

```js
app.checkpoint("before-update");   // state + 权限表 + 资源账本 + 故障计数
app.rollback("before-update");     // 恢复 signal（有界批次重渲染）+ 账本，然后同步 flush
app.snapshot();                    // 只读快照：state / policy / permissions / resources / tasks
```

**DOM 不拍照**：回滚只恢复可变状态与账本，结构靠 scope 重建 + 视图重跑回到一致状态。
理由很简单：深拷贝 DOM 的成本随界面线性增长，而 0.6 的目标是「大型项目也能扛」。
`fault: "rollback"` 会自动使用最近一个检查点。

## 8. 兼容性与破坏性变更（0.4 → 0.6）

| 项 | 影响 | 处理 |
| --- | --- | --- |
| `ABI_VERSION` / `BYTECODE_VERSION` | 破坏性 | 预期内；v1/v2 文件仍可装载 |
| `.jbc` 输出体积 | 略增（3 个段） | 可接受；解码器跳过未知段，前向兼容 |
| `fault: "report"` | 语义不变 | 归一化为 `recover` |
| `fault` 默认值 | **需注意**：内核默认仍是 `"stop"`，`Runtime` 默认 `"recover"`（与 0.4 的 `"report"` 一致） | 无需改动调用方 |
| `handle.permissions()` | 结构不变 | 新增 `handle.capabilities()` 提供 0.6 视图 |
| `handle.inspect()` | 键集合**不变**（有测试锁死） | 新指标走 `profile().counters` |
| `policy.capabilityAllowlist` | 仍有效 | 新的 `capabilities` 树是它的超集 |
| `describe()` / `describePolicy()` | 新增只读键 | 旧消费方读老键即可 |

## 9. 路线图（0.6.0 已完成，其余分轮推进）

### 0.6.0 VM 基础升级 —— **本轮已完成**

```
✓ ABI v3（CAPABILITIES / RESOURCES / FLAGS + 未知段跳过）
✓ Multi-pass Verifier（11 趟 + CFG + 抽象栈类型 + strict 档）
✓ Capability Graph + Permission Kernel（状态机 / 租约 / 祖先授权 / 运行中撤销）
✓ Resource Kernel（14 类资源 / ENOSPC_QUOTA / 统一账本）
✓ Scheduler v2（P0..P7 通道 + 任务 + 预算 + 截止时间）
✓ Cooperative Yield（挂起 → 让出 → 续跑，可续跑规则 + 预算错误兜底）
✓ Fault Ladder 六级 + Error Boundary（组件级 restart）
✓ Checkpoint / Rollback
✓ 诊断面（profile / snapshot / CFG dump / 热点函数）
✓ EACH 分片渲染（renderChunk / frameBudgetMs / 幂等重入，见 0.6.1）
```

## 10. 一条红线

0.6 让 VM 变成宿主资源的唯一仲裁者，但**不能突破浏览器本身**：
CORS、CSP、Permissions、跨源 Cookie、iframe sandbox、HTTPS、进程沙箱——
这些是平台边界，不是内核缺陷。能力图的意义在于「在浏览器允许的范围内，
每一次跨界都必须经过内核授权并留下账本」，而不是假装能越狱。
